### 2: Clarifying How JavaFX Talks to the Page's DOM

- The bridge between JavaFX and the loaded HTML page is WebEngine — it's the object underneath WebView that actually manages the page and lets Java code run JavaScript against it.
- executeScript(...) is the method that sends a JavaScript string to the loaded page and runs it — this is how a Java-side button click can actually reach into and change the DOM.
- Clarified that this direction (JavaFX → page) is simpler than the reverse (page → JavaFX callbacks), which is why it makes sense to implement this direction first and treat any page-to-Java communication as a later addition if needed.

### 3: Planning the Dynamic Text/Color Change Behavior

- Agreed on the specific demo: a button that changes a piece of text on the page, and a separate action that changes its color — matching the "before/after" comparison style the professor wanted to see clearly.
- The JavaScript run via executeScript would target a specific HTML element (e.g. by id) and modify its innerText or style.color — small, targeted DOM changes rather than reloading or rewriting the whole page.
- This keeps the implementation scope tight and testable: each button maps to one obvious, verifiable change, which is easy to demo and easy to debug if something doesn't work.

### 4: Comparing Notes With Other Teams
