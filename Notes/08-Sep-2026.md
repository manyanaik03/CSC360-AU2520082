### 1: Exceptions, Assertions, and Logging

- An exception is Java's way of signaling something went wrong at runtime — try/catch lets code handle it instead of crashing outright, and throw/throws lets a method raise or declare one.
- Checked exceptions (like IOException) must be caught or declared; unchecked exceptions (like NullPointerException) don't force that — this distinction is Java's way of separating "expected failure modes" from "programming bugs."
- assert is a lightweight sanity check meant for development/testing — it's disabled by default at runtime unless explicitly enabled with -ea, so it should never replace real error handling.
- Logging (e.g. java.util.logging or a framework like SLF4J) records what a program did over time — unlike a println, logs usually have levels (INFO, WARNING, SEVERE) so output can be filtered without changing code.

### 2: Idea of Generic Programming

- Generics let a class or method work with any type while still catching type errors at compile time — e.g. List<String> guarantees only Strings go in, without needing a cast when reading them back out.
- Before generics, collections stored plain Object, meaning a wrong-type item wouldn't be caught until it caused a ClassCastException at runtime — generics move that error earlier, to compile time.
- A generic method/class uses a type parameter (commonly T, E, K, V) as a placeholder — the actual type gets filled in wherever it's used, without writing separate code for each type.

### 3: Collections

- Collections are used to store and manipulate groups of objects.
- Common Java collections include `List`, `Set`, `Queue`, and `Map`.
- `ArrayList` stores elements in an ordered list and allows duplicate values.
- `HashSet` stores unique elements.
- `HashMap` stores data using key-value pairs.
- Collection methods such as `add()`, `remove()`, `contains()`, `get()`, and `size()` are commonly used.

```text
                         Collections
                              |
          +-------------------+-------------------+
          |                   |                   |
         List                Set                Map
          |                   |                   |
      ArrayList            HashSet            HashMap
          |                   |                   |
     Ordered data       Unique data       Key-Value data

```
### 4: Views

- A "view" is a live window onto an existing collection, not a copy — e.g. map.keySet() gives back the actual keys backed by the map itself, so changes to one are reflected in the other.
- This matters because modifying a view can modify the original data structure too — removing an item from a keySet() view actually removes that entry from the underlying map.
- Views are used to avoid unnecessary copying — getting "just the keys" or "just a sub-range" of a list doesn't need a whole new data structure, just a different way of looking at the same one.


### 5: Events and How Events Connect to Graphics

- An event is something that happens at runtime — a click, a key press, a slider drag — and JavaFX represents each one as an object carrying details about what happened.
- Connecting an event to graphics means attaching an EventHandler to a UI node (like a Button), so that when the event fires, a specific block of code runs — often code that updates something else on screen.
- The key idea: nothing happens on screen until an event triggers it — drawing/updating graphics in response to user interaction is fundamentally different from drawing once and being done.

```text

          Mouse Click          Keyboard Input
              |                     |
              +----------+----------+
                         |
                       Event

                  Event Handler

```

### 6: Layouts

- A layout pane decides how child components are automatically positioned and resized — instead of manually setting x/y coordinates for every element.
- Common ones: VBox (stacks children vertically), HBox (horizontally), BorderPane (top/bottom/left/right/center regions), GridPane (rows and columns).
- Choosing a layout is really choosing a positioning *rule* — the layout recalculates positions automatically if the window is resized, which manual coordinates never would.

### 7: Slider

- A Slider lets a user pick a numeric value by dragging a handle along a track, instead of typing a number.
- Key properties: min/max define the range, value holds the current position, and a listener on valueProperty() lets other code react live as the user drags — not just after releasing it.
- Useful anywhere a continuous or bounded value is needed interactively — brightness, volume, zoom level, etc.

 ```text

            0                                             100
            |----------------------------------------------|
                         ●
                    Slider Thumb

                    Current Value
```

### 8: Dialogs

- A Dialog is a small secondary window used to get a quick decision, input, or show a message, without building an entirely separate application window for it.
- Alert is the common built-in dialog type — with built-in variants for information, warning, error, and confirmation, each with sensible default buttons already set up.
- Dialogs are typically modal — meaning the rest of the application waits/is blocked until the dialog is closed or answered.

### 9: Combining Swing and JavaFX in One UI

- SwingNode is the bridge that lets a Swing component be embedded directly inside a JavaFX scene graph, so both toolkits can appear in the same window.
- This matters for reusing older Swing components (like specific widgets) that don't have a direct JavaFX equivalent yet, without rewriting them.
- Practical detail: Swing components must be created and modified on Swing's own thread (via SwingUtilities.invokeLater), while JavaFX components use the JavaFX Application Thread — so mixing them means being careful about which thread touches which part.

```text

              |             |             |
            Label         TextField      Button
                                           |

```

### 10: Master-Detail Layout

- Master-Detail is a UI pattern where one panel shows a list of items (the "master") and another panel shows full details of whichever item is currently selected (the "detail").
- Typically built with a layout like BorderPane: the master list (e.g. a ListView) on one side, and a details panel on the other side or in the center.
- The connection between them is event-driven: selecting an item in the master list fires a listener that updates what's displayed in the detail panel — same underlying idea as Topic 6 (events connected to graphics).

```text
               Master - Detail Layout
                           |
             +-------------+-------------+
             |                           |
          MASTER                       DETAIL
             |                           |
          ListView                    Label
             |                       TextField
        Select Item                  Image/Data
             |                           |
             +---------- Event -----------+
                         |
                  Update Details
```

### 11: Styling a Single Geometric Object

- JavaFX shapes (Circle, Rectangle, etc.) can be styled either through direct properties (setFill, setStroke, setStrokeWidth) or through CSS-style properties (-fx-fill, -fx-stroke) set via setStyle().
- A small UI (sliders, color pickers, etc.) can be built to let the user adjust these properties live, binding each control's value directly to the shape's corresponding property.
- This ties directly into Topic 8 (Slider) — a slider bound to something like radius or strokeWidth is a common way to let a user visually adjust a shape's properties in real time.

### 12: JavaFX with Browser (WebView) Support

- WebView is JavaFX's embedded browser component, built on WebEngine — it can load and render actual web pages inside a JavaFX window.
- A button click in JavaFX can reach into the loaded page's DOM using WebEngine.executeScript(...), running JavaScript that changes the page's content, styles, or structure from the Java side.
- This is a two-way bridge: JavaFX calls into the page via executeScript, and the page can call back into Java code too (via a JavaScript-to-Java bridge object), though the simplest direction — Java controlling the DOM — is usually where this starts.
```text
                JavaFX Application
                           |
                         Button
                           |
                    Event Handler
                           |
                     WebEngine
                           |
                    JavaScript Code
                           |
                         DOM
                           |
                  Web Page Changes
```

**Q&A Discussed:**

- Q: Why does Java disable assertions by default?
  A: Assertions are meant for catching bugs during development — leaving them on in production would add runtime overhead for checks that shouldn't fail in correctly working code anyway.

- Q: Why did generics get introduced to Java collections?
  A: Before generics, collections stored plain Object, so a type mismatch only surfaced as a ClassCastException at runtime — generics catch that mistake at compile time instead.

- Q: What's the practical risk of using a collection view like keySet()?
  A: Since it's backed by the same data, removing an item from the view actually removes that entry from the original map — not just from what you're looking at.

- Q: Why does mixing Swing and JavaFX require thread awareness?
  A: Swing components must be touched from Swing's own thread, and JavaFX components from the JavaFX Application Thread — mixing them carelessly can cause threading bugs that don't show up consistently.

- Q: In the WebView/DOM task, which direction is simpler to implement first?
  A: JavaFX controlling the page via WebEngine.executeScript() — the reverse direction (page calling back into Java) needs an extra bridge object set up first.
