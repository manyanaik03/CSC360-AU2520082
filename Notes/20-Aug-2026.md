\### 2: Inheritance, extends, super, and @Override



\- A subclass reuses an existing class's fields/methods via extends — e.g. a custom panel class extending JPanel inherits everything JPanel already knows how to do (sizing, borders, repainting) without rewriting it.

\- super refers to the parent class specifically — used to call the parent's version of a method before adding custom behavior on top, rather than replacing it outright.

\- @Override isn't required to override a method, but it's a safety net: the compiler checks the method signature actually matches something in the parent class. Without it, a typo'd method name silently becomes a brand-new unused method instead of an override — a bug that's hard to notice visually but easy to catch with this annotation.

\- Practical rule of thumb: if you're overriding a Swing lifecycle method (paintComponent, actionPerformed, etc.), always add @Override — it turns a silent mistake into an immediate compile error.



\### 3: Why super.paintComponent(g) Comes First



\- Swing panels don't erase themselves automatically between frames — each repaint draws on top of whatever was already there unless told otherwise.

\- Calling the parent's paintComponent(g) as the very first line clears the panel back to its background color/state before any custom drawing runs.

\- Skipping this step causes old shapes to visually "smear" or persist across repaints, since new drawing commands just layer on top of stale pixels instead of a clean canvas.

\- This matters more than it looks like a formality — it's the difference between a stable, correctly redrawn UI and one that visually corrupts itself after a few updates (e.g. window resize, minimize/restore).



\### 4: Filling a Triangle — Point-Inside Test Using Edge Functions



\- Unlike a rectangle, a triangle can't be filled with a single built-in method — its interior has to be tested pixel by pixel.

\- Step 1 — Bounding box: find the smallest rectangle that fully contains the triangle (min/max of the three vertices' x and y), so only that region needs checking instead of the whole canvas.

\- Step 2 — Edge function per side: for each edge between two vertices, there's a formula (based on the cross product of the edge vector and the vector to the test point) that tells you which side of that edge a given pixel falls on — positive on one side, negative on the other, exactly zero if it's on the line.

\- Step 3 — Inside test: a pixel is inside the triangle only if it falls on the \*same\* side of all three edges consistently — i.e. all three edge-function results share the same sign. If the vertices are listed in a consistent rotational order (all clockwise or all counter-clockwise), "inside" simply means all three results are ≥ 0 (or all ≤ 0, depending on that ordering).

\- This is essentially how graphics hardware rasterizes triangles at a low level — the same reasoning scales up to how GPUs fill polygons in real time.

\*\*Q\&A Discussed:\*\*



\- Q: Why use @Override if the method works fine without it?

&#x20; A: It only matters when there's a mistake — a mismatched signature fails silently without it, but throws a compile error with it.



\- Q: What actually breaks if super.paintComponent(g) is left out?

&#x20; A: Nothing crashes — but old drawings stay on screen and new ones draw on top, causing visual smearing over repeated repaints.



\- Q: Why check a bounding box instead of every pixel in the whole window?

&#x20; A: It limits the per-pixel edge-function checks to a much smaller region, since the triangle can only exist within its own bounding box.



\- Q: How does the edge function decide "inside" vs "outside"?

&#x20; A: Each edge splits the plane into a positive and negative side; a pixel is inside only when it lands on the same side of all three edges.
