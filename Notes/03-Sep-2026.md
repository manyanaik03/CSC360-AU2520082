### 1: Printing a Binary Tree as ASCII Art

- The tree itself is just a plain Node class (value + left + right) — none of the printing logic lives inside the node, exactly like the earlier drawing version, except now the "canvas" is the console.
- The recursive method carries two extra things down with it: a `prefix` string (built up so far) and a flag telling it whether the current node is the "last child" at its level.
- The connector characters do the visual work: `├──` for a node that has a sibling coming after it, `└──` for the last child at that level — this is what makes the branches look continuous or terminated.
- When recursing into children, the prefix is extended differently depending on the flag: `│   ` (a vertical bar + spaces) if this node was NOT the last child, or just spaces if it was — that's what keeps the vertical guide lines lining up correctly for deeper levels.
- Typically the right child is printed first (top) and the left child second (bottom), so that when read top-to-bottom in the console, it visually mirrors how the tree would look if drawn sideways.

### 2: Drawing Arrows Between Two Lists That Share Elements

- The setup is two lists (List A and List B) rendered as two vertical columns — each item gets a fixed (x, y) slot based on its index in its own list.
- Instead of comparing every item of A against every item of B with a nested loop, the faster approach is building a HashMap (or HashSet) of List B's values mapped to their index — turning an O(n×m) search into an O(n+m) one.
- For every item in List A, we just ask the map "does this value exist in B, and at what index?" — if yes, we now have both coordinates needed to draw a connector between them.
- The actual arrow reuses the same trig idea as the tree-connector arrows from before: find the angle between the two points with `Math.atan2()`, shorten the line so it starts/ends at the edge of each box (not the center), then add two short angled lines at the tip to form the arrowhead.
- Duplicate values need a decision up front — does the program connect to the *first* matching index, *all* matching indices, or the *nearest* one? This has to be settled before writing the lookup logic, or the arrows come out wrong for repeated elements.

```
           List A                          List B
        +-----------+                  +-----------+
        | itemA[0]  |                  | itemB[0]  |
        | itemA[1]  |----- common? --->| itemB[1]  |
        | itemA[2]  |                  | itemB[2]  |
        +-----------+                  +-----------+
               |
     For each item in A:
       lookup value in HashMap(B)
               |
        found? ---- yes ----> get index in B --> draw arrow (A[i] -> B[j])
               |
              no  ----> skip, no arrow
```

### 3: JavaFX Splash Screen Built With FXML

- A splash screen is really just a second, smaller `Stage` shown *before* the main stage — usually created with `StageStyle.UNDECORATED` (or `TRANSPARENT`) so it has no title bar/borders and looks like a proper loading screen.
- The splash's layout (logo, progress bar, loading text) lives in its own `splash.fxml`, separate from the main app's `main.fxml` — each with its own controller class.
- Because loading real data (or just simulating a delay) on the JavaFX Application Thread would freeze the UI, the "work" is wrapped in a `Task`, run on a background thread — the splash's progress bar binds directly to the Task's `progressProperty()`.
- The flow in `start()`: load and show the splash stage first → start the background Task → when the Task finishes (`setOnSucceeded`), close the splash stage and load/show the main stage.
- Charts (e.g. `LineChart`, `PieChart`) can be declared directly inside FXML using their tag names, with axes also defined in FXML — the controller then just grabs the chart via `@FXML private LineChart<...> chart;` (matched by `fx:id`) and pushes in a `Series` of data once the main screen is showing.

                Application.start()
                        |
              Load splash.fxml -> show Splash Stage
                        |
              Create + start background Task
              (simulated loading / data fetch)
                        |
              progressProperty <-- bound --> ProgressBar
                        |
               Task onSucceeded?
                        |
                  Yes --+-- No (show error / retry)
                        |
              Close Splash Stage
                        |
              Load main.fxml -> show Main Stage
                        |
              Controller (@FXML chart) adds Series
              (LineChart / PieChart populated)

**Topics Covered:**

- Efficient lookup between two lists using a HashMap instead of nested loops
- Reusing the earlier arrow-drawing trig logic for a new "matching elements" context
- Structuring a JavaFX app around a splash Stage + main Stage using separate FXML files
- Running background work in JavaFX with `Task` so the UI thread never freezes
- Declaring and populating charts (LineChart/PieChart) defined in FXML

**Reflections:**

- **ASCII tree printing:** The part that didn't click immediately was how the *prefix string itself* changes shape as it's passed deeper — it's not just indentation, it's actively deciding whether a `│` needs to keep appearing at that column or not.
- **List-to-list arrows:** Realized this is basically the same "connect two points with an arrow" problem as the circle-connector project, just with the point coordinates coming from list indices instead of mouse clicks — the trig math didn't need to change at all.
- **HashMap vs nested loop:** Understood why checking "is this in the other list" one item at a time with `.contains()` on a list is fine for small inputs but turns slow fast — building the index map once up front is the fix.
- **Splash screen timing:** The key realization was that the splash screen isn't "shown for N seconds" on a timer — it's shown *until the background Task finishes*, which just happens to look like a fixed delay when the work is simulated.
- **FXML + charts:** Didn't expect charts to be declarable as plain FXML tags like any other UI control — the controller only has to worry about the data (Series), not about laying out the axes.

**Key Terms:**
recursive tree printing · prefix string · `├──` / `└──` connectors · HashMap lookup · O(n×m) vs O(n+m) · `Math.atan2` (reused) · arrowhead angle · `Stage` / `StageStyle.UNDECORATED` · FXML controller · `Task` / `progressProperty()` · `setOnSucceeded` · `@FXML` injection · `fx:id` · LineChart/PieChart in FXML

**Q&A Discussed:**

- Q: Why print the right child before the left child in the ASCII tree?
  A: So that when the output is read top-to-bottom in the console, it visually matches how the tree would look if it were rotated and drawn sideways on paper.

- Q: Why not just use a nested loop to compare List A and List B directly?
  A: A nested loop checks every pair, which is O(n×m) and gets slow as the lists grow — building a HashMap of one list's values first turns each lookup into a constant-time operation.

- Q: What happens if the same value appears more than once in both lists?
  A: The program needs a rule decided in advance (first match, nearest match, or all matches) — without one, the arrow-drawing logic won't know which index in the other list to connect to.

- Q: Why does the splash screen need a background `Task` instead of just calling `Thread.sleep()` directly?
  A: Calling `Thread.sleep()` on the main JavaFX thread would freeze the whole UI (including the progress bar animation) — a `Task` runs the delay/work on a separate thread so the UI stays responsive.

- Q: How does the chart in the main screen get its data if it's declared in FXML?
  A: The FXML only defines the chart's structure (axes, type); the controller retrieves the chart object via its `fx:id`, then builds and adds a `Series` of data to it in code, usually right after the FXML loads.
