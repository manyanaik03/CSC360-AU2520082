### 1: What the Project Review Actually Checks

- Evaluation isn't only about the finished product — it also checks whether each person on the team can actually explain how their own and others' parts work, not just that the feature runs.
- Scope discipline matters more than feature count: building exactly what's required cleanly is rated higher than a longer feature list that's harder to follow or maintain.
- A reviewer judging the project needs the documentation to explain *how things work*, not just list what was built — the workflow has to be traceable from the written notes alone, without someone standing there to narrate it.
- Practical prep for this: being able to point at any class or method and explain its purpose on the spot is treated as proof of real understanding, separate from whether the code itself works.

### 2: Reusable Code Through Generic Programming

- The core idea of generic programming is writing one version of a logic block that works across multiple data types, instead of duplicating the same logic with only the type changed.
- Simple way to remember it: write the logic once, and let it be reused for whatever type is plugged in later — the type becomes a variable the same way a value would be.
- The payoff isn't just less typing — it's that a bug fix or improvement made once in the generic version applies everywhere it's reused, instead of needing to be repeated in every type-specific copy.

### 3: Treating Different Shapes Through One Common Abstraction

- JavaFX groups shapes like lines, circles, and rectangles under a shared `Shape` concept, so operations that apply to "any shape" don't need to be rewritten separately for each specific kind.
- Instead of handling every shape type as a completely separate case, common behavior is written once against the shared abstraction and reused across all of them.
- Actually getting pixels onto the screen goes through a drawing mechanism (a graphics context) that takes a shape's data and renders it — the shape itself is just a description; the graphics context is what turns that description into something visible.

### 4: Separating What a Shape Is From How It Looks

- Every graphical object really has two separate categories of information: its geometry (what it is and where it sits) and its appearance properties (how it's rendered once placed).
- A concrete example is a line's thickness — thickness doesn't change the line's position or endpoints at all, it only changes how prominently that already-defined line is rendered.
- Keeping these two categories distinct is what allows a shape's visual style to be adjusted independently of its underlying geometric definition.

### 5: Mutable and Immutable Objects

- A mutable object allows its internal state to be changed after it's created — the same object reference can hold different values at different points in time.
- An immutable object locks in its state at creation — once built, nothing about it can be altered; any "change" has to produce a new object instead.
- Quick way to hold onto the distinction: mutable means it can still change, immutable means it cannot.
- This matters practically because changing an existing mutable object versus creating a brand-new immutable one can lead to very different behavior elsewhere in a program, especially if other code is still holding a reference to the original object.

- **Geometry vs. properties:** Thickness not touching a line's actual position was the clearest example of why these two ideas are kept separate — one defines the object, the other just adjusts how it's shown.
- **Mutable vs. immutable:** The real risk isn't the concept itself, it's forgetting which kind of object you're working with — changing a mutable object in place can quietly affect other code still referencing it, which an immutable object avoids by design.

**Q&A Discussed:**

- Q: Why does the project evaluation check individual understanding instead of only the final build?
 A: Because a working feature doesn't prove the person who built it (or their teammates) actually understands how it works — being able to explain it on request is a separate, more reliable check.

- Q: What's the actual benefit of generic programming beyond saving typing?
 A: A fix or improvement made once in the shared generic logic automatically applies everywhere it's reused, instead of needing to be repeated across every type-specific copy.

- Q: Why group different shapes under one Shape abstraction instead of handling each separately?
 A: So operations that apply to any shape can be written once and reused, rather than duplicating the same logic for lines, circles, and rectangles individually.

- Q: Why does changing a mutable object risk unexpected behavior elsewhere in a program?
 A: Other code might still be holding a reference to that same object — changing it in place changes what that other code sees too, which an immutable object avoids since it can never be altered after creation.
